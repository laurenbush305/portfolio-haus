## Business review

The homepage explicitly positions Portfolio Haus as strategic communications and messaging for institutions **and** expert-led founders. Institutional work is prominent in the hero and first pathway, with policy, programs, public trust, research and stakeholder alignment described. This remains a broader consultancy, not a founder-only business.

Doctrine Build™ is visible on the homepage and Institutional/Method pathways and explained as Diagnose / Design / Deliver, with outputs and a working example. Method headings now follow the page hierarchy without changing their appearance.

The current primary navigation is **Home, Institutions, Founders, Work, About, Start**. These are the deployed labels, not the older list in the brief. Method, The Receipt Rule and Tools are footer links; the homepage also links Method and the diagnostic. Ways to Work is a useful noindex pathway chooser; Contact is a noindex compatibility page canonicalized to Start. These routes are intentional, working and retained.

Credibility is supported by attributed prior-role cases covering federal healthcare training, financial education and association communications, plus Lauren’s named experience and accountable senior-lead model. Prior employers and the origin of the work are disclosed. This audit checked the presentation and links; it did not independently substantiate every business metric or client permission. No new endorsements, client logos, service claims or procurement details were invented.

Inquiry calls to action lead to Start and accept relevant pathway/offer/diagnosis prefills. The local inquiry flow is usable and candid, but requires the prospect to send an email after preparing it. That is an owner decision about lead collection, not a broken delivery integration.

Can They Repeat It?™ is discoverable from the homepage and Tools. Its ten-question flow produces six possible diagnoses; all six across four buyer contexts were tested (24 combinations). Institutional, founder, opportunity and unsure recommendations point to the existing architecture. Back/restart, downloadable results and inquiry prefilling work. There is currently no conversion measurement. Any shortening of the pathway or new capture requirement should follow an approved measurement/UX decision.

## C. Fresh verification results

- **Build:** actual `bundle exec jekyll build --strict_front_matter` with the existing Jekyll 3.10.0 lockfile: pass. The baseline main build also succeeded.
- **Static regression:** `python3 scripts/check-site.py _site`: pass for 18 HTML pages, internal routes/assets/fragments, unique metadata, JSON-LD, canonical/OG consistency, exactly ten sitemap URLs, noindex pages, robots and documentation/source exclusions.
- **Syntax/whitespace:** 11 external/inline JavaScript checks, browser-test syntax and `git diff --check`: pass. No project lint or type-check command exists; this site has no TypeScript/compiler or production Node build.
- **Browser suite:** existing `tests/browser.cjs`: pass, including 18 routes at four widths, 24 diagnostic/context combinations, navigation/Escape/keyboard, native FAQ, local intake required/email validation, exact inquiry download and denied-clipboard fallback, both working tools, five Signal lanes/free-text/XSS-text handling, no-JS fallback, and no page errors or local asset failures.
- **Test harness boundary:** because the managed preview is not reachable from the executor’s headless browser, the existing browser suite read the actual built bytes through a test-only virtual origin. Exact hosted font CSS/assets were cached for deterministic rendering. This was not a real HTTP deployment test. Real production HTTP status/metadata/assets were independently retrieved; the managed preview and live inquiry were independently exercised in the cloud browser.
- **CTA matrix:** 1440×900, 1366×768, 1024×768, 768×1024, 390×844, 375×667, 320×568: CTA entirely visible and unobstructed after remediation. Initial 320×568 failed.
- **Visual preservation:** before/after homepage viewport screenshots at 1440×900, 390×844 and 375×667 were byte-for-byte identical in the controlled comparison. The 320×568 compact adjustment is intentional. Images, brand fonts, palette and content preserved.
- **Accessibility automation:** axe-core scan with WCAG 2 A/AA, 2.1 A/AA and 2.2 AA tags: zero violations across 18 default pages, both invalid tool states and open Signal panel (21 states). Some color-contrast and label/name checks were returned as incomplete and still require manual review. This does not certify full WCAG compliance or assistive-technology behavior.
- **Live HTTP:** all 18 known routes returned 200; deliberately invalid URL returned branded HTTP 404. Robots, sitemap, social image and three favicon assets returned 200. Ten indexable titles/descriptions were distinct; no content img lacked alt. Compatibility/tool exclusions correct.
- **Inquiry:** live missing-field and invalid-email checks correctly block preparation; valid data reveals editable review and focus. No live POST or email sent. Optional Formspree is blank in configuration, so inbox delivery and server failure handling cannot be tested.
- **Performance:** controlled delayed-script local comparison proves the specific layout-shift repair. Lighthouse 13.5 attempted mobile/desktop but produced document certificate errors, not usable scores. PageSpeed API returned 429 quota exhausted. Previous PR scores are historical, not new results. No real-user p75 LCP/INP/CLS or production CWV pass established. Target LCP ≤2.5s, INP ≤200ms, CLS ≤0.1 at the 75th percentile, measured separately for mobile and desktop; no universal two-second load requirement.
- **Not completed:** authenticated social-platform preview/cache checks, Search Console/CrUX account data, receiving mailbox test, optional connected form real success/failure, physical iOS/Android, Safari/Firefox and screen-reader speech testing. Production deployment/retest is outstanding.

## D. Outstanding decisions and access

1. **Privacy policy:** approve accurate language and a footer/Start link after confirming business/controller details, contact, data purposes, retention, hosting/font/email providers, applicable audience/jurisdictions and rights process. Decide whether to self-host the existing fonts. No policy or banner should imply nonexistent tracking or delivery.
2. **Inquiry delivery:** keep local preparation/email, or authorize a verified Formspree endpoint. Enabling it requires owner account/recipient verification, review of processor terms/retention/spam settings and one explicitly authorized test through to the receiving inbox, including success and failure behavior.
3. **Analytics:** decide whether measurement is wanted and approve provider/consent approach. Candidate non-sensitive events: pathway selection, diagnostic start/completion, inquiry prepared and email-draft opened. Never send name, email, organization, free text, generated briefs or full query strings. Record an actual inquiry submission only after a real processor success, not a draft click.
4. **External verification:** mailbox access/test authorization, social sharing debugger access and Search Console/field data access where available.
5. **Release:** review/merge the consolidated PR, then verify GitHub Pages deployment and retest the live domain. Draft status has been preserved; no deployment is represented as complete.

## E. Prioritized recommendations

1. **Security, privacy and reliability:** approve and publish the accurate privacy policy; verify the receiving mailbox. Choose the intended inquiry flow before connecting any processor. Keep secrets out of this static repository. The noindex working tools are publicly reachable, not access-controlled.
2. **Accessibility and mobile:** release the validated mobile/validation fixes; finish manual contrast/name review and physical-device, Safari/Firefox and screen-reader testing.
3. **SEO/discoverability:** verify rendered social previews and Search Console after release. Preserve current canonical/sitemap exclusions. Self-hosting the same licensed fonts is an optional privacy/performance improvement requiring an agreed maintenance approach.
4. **Lead generation/conversion:** decide on direct delivery and minimal analytics; measure diagnostic-to-inquiry progression before changing capture steps or persistent CTAs. The current institutional/founder positioning and service sequence should remain intact.
5. **Optional enhancements:** only add a sticky CTA, new thank-you page, procurement collateral or new navigation content if measured behavior or a confirmed buyer requirement justifies it. None is necessary simply to complete a checklist.
